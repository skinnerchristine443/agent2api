## 1. 上游变化追踪

### 1.1 变化的三个来源

上游变化分三类，**客户端版本只是其一**；后两类没有版本号、最容易漏：

| 来源 | 特征 | 怎么发现 |
|---|---|---|
| **客户端更新** | 有版本号、可见 | 发版时对照新版安装包（`build-manifest.json` / `Info.plist` + `app.asar` 抽查关键协议点） |
| **服务端静默改版** | 无信号、最险 | 生产信号（错误码 / 签到结果 / 模型目录）+ 定期「用前必核」 |
| **活动与规则变化** | 运营面、影响拿分 | 活动页 / 公告 + 真机实测 |

### 1.2 追踪面清单

逐面核对；「盯什么」与已知变更信号形态如下（→ 指向 §2 对应契约）：

1. **鉴权与凭证** —— 刷新端点 / 刷新头取值 · client id 绑定（旧 client 铸造的 token 换新 client 刷新会被拒）· 凭据新形态（加密信封）→ §2.1 / §2.5
2. **签到 / 活跃打卡** —— 时间窗与发放判定 → §2.2 / §2.4
3. **额度体系** —— 三种制式（日额度 / 约 30 天 / 5h+周滚动）· 到期字段与占位阈值 · 结算域 → §2.3
4. **模型目录与倍率** —— 模型 id / 能力 / 按客户端标识分桶 · 倍率文本（极易过期，用前必核）
5. **出站协议与风控** —— 请求体白名单 · 出站逐字指纹（反探测数字串等）· 裸 403 整源封锁 · 限流头 → §2.6
6. **错误码与响应形态** —— 业务码台账 · bool / int / 数字字符串混用（必须宽松解析）→ §2.6
7. **模型行为** —— 工具调用泄漏（DSML 标记文本）格式 · 思考档位表达（防护口径见 `docs/02` §4）
8. **活动与政策规则** —— 领取 / 发放政策的公告变化 · 风控红线 → §2.2 / §2.4

### 1.3 变化如何发现

- **客户端侧**：发新版时对安装包做协议抽查——WorkBuddy 读 `Info.plist`（版本）并对 `app.asar` 扫关键协议字符串（刷新头 / 端点 / 信封方案）；Trae 以官方渠道与安装包为准。
- **服务端侧**：读生产信号——控制台观测（错误码 / 签到结果 / 模型目录）；经验判据：**修复后长时间无新错误 = 稳定**；另按 §3 待核清单定期主动核实。
- **外部渠道**：官方渠道 / 社区实现 / 公告——**只作线索、不作依据**（同源不算交叉印证；上游事实以代码与实测为准）。社区实现的逐项目跟踪清单见 `private/参照项目跟踪清单.md`（含项目名，不随仓库分发）。

### 1.4 变化如何适配

1. **取证坐实**（真机 / 抓包 / 探针；未取证不编码）；
2. **生产止血**（如需：数据层修复或配置止血，先于代码改动）；
3. **代码适配 + 护栏**（新护栏用反向注入证明会失败并点名）；
4. **契约与记录同步**（更新本文件对应节 + `docs/03-更新记录.md`）。

> 先例（完整处理见 `docs/03`）：Trae 旧 client 绑定（刷新被拒 → 数据层批量修复 → 代码侧补齐）；凭据加密信封（只识别、明确报错，不解密）。

## 2. 契约台账

> 编号对照：旧版 §1–§7 → 现 §2.1–§2.7。

### 2.1 令牌刷新（v2 plugin）

- 端点：`POST /v2/plugin/auth/token/refresh`，body `{}`
- 请求头：
  - `X-Refresh-Token: <refresh token>`
  - **`X-Auth-Refresh-Source: plugin`** ← 值必须是 `plugin`。该头决定刷新会话的客户端归属；值错 / 缺失时**国际版**返回 `invalid_grant`（业务码 **12153**，`Offline user session not found`）。
  - ⚠️ **CN 取值未实测**：存在相反信号（称 CN 应为 `workbuddy`）⇒ 真机 A/B 列入待核；**取证前不写区域条件分支**。
  - `X-Domain: <authority>`（上游客户端按认证端点的 authority 填）
  - 企业账号在**通用请求**上另有 `X-Enterprise-Id` / `X-Tenant-Id`；**刷新请求只发 `X-Domain`**。
- 响应：`{code,msg,data:{accessToken,refreshToken,expiresAt...}}`
- 客户端侧路径形态（2026-10-09 本机客户端 asar 实读）：`/v2${prefixPath}/auth/token/refresh`（`prefixPath` 变量注入，即 `plugin` 段的位置）与 `/v2/auth/token/refresh` 两种写法并存；内置路由表以 `pathPattern: /v2/*/auth/token/refresh` 归档。
- 核实：**2026-10-06**，对照上游客户端自身实现（`refreshSession`，3 处 `X-Auth-Refresh-Source` 全为 `plugin`）；**CN 取值未见实证**（见文末待核清单）。
- 代码：`internal/providers/workbuddy/headers.go`（`RefreshSourcePlugin`）。

### 2.2 每日签到与签到状态（CN 专属）

> `checkin-activity-status` / `daily-checkin` 都是**国内版专有**。其它区域的领取路线：**Global → 网页会话活跃打卡**（本仓实现）；**Intl → 未实现**（其 token 会被 CN 网关拒绝）。⚠️ Global 是否另有「计费端点」路线，存在冲突信号 ⇒ 待核（见文末清单）。

- 状态：`POST /v2/billing/meter/checkin-activity-status`，body `{}`
  - 字段：`active`(bool) · `activity_name` · `today_checked_in`(bool/1) · `today_credit` / `daily_credit` · `streak_days` · `total_credits` · `is_streak_day` · `next_streak_day`
  - 同一 key 在不同 realm / 版本会给 bool / int / 数字字符串 ⇒ **必须宽松解析**（`internal/providers/workbuddy/checkin_status.go`）。
- 领取：`POST /v2/billing/meter/daily-checkin`，body 字面量 `{}`
  - 「已签」判定：业务码 `10001`、`msg` 含「已签」、或响应为 `null`。
- 核实：**2026-10-06**（字段名与宽松解析假设）；**本仓尚未有 CN 真机抓包** ⇒ 待核。

### 2.3 额度包（get-user-resource）

- 端点：`POST /v2/billing/meter/get-user-resource`
- 请求体关键项：`PageNumber` · `PageSize` · `ProductCode="p_tcaca"` · `Status=[0,3]` · `PackageEndTimeRangeBegin/End`
- 响应：`data.Response.Data.Accounts[]` + `TotalDosage`
- 到期字段：**用 `CycleEndTime`**（`"2006-01-02 15:04:05"`，UTC+8 墙钟）
  - 上游另存在**十年尺度的占位到期值**（如 2049 类）与真实周期到期并存；判据：距当前 **> 730 天**即视为长期占位，不计入到期与「即将过期」排序。
  - 包身份字段：`ResourceId` / `ResourceCycleId` / `PackageCode`（**没有** `PackageId`，**没有** `CycleBeginTime`）。
- 核实：**2026-10-06**（`CycleEndTime` 由本仓既有真机抓包确认；730 天判据来自真实数据上的踩坑记录）。

### 2.4 成长中心（`/v2/activity/growth/*`，CN）

- 读：
  - `GET /buddy/travel/status` → `state`（`"arrived"` 可领）· `record_id` · `daily_limit_reached`
  - `GET /buddy/travel/config`
  - `GET /tasks` → `tasks:[{task_code,title,locked,accept_status,reward_credit,reward_energy}]`
  - `GET /streak` → `streak:{days,makeup_dates:[...]}` · `launch_date`
  - `GET /heatmap` → `today:{date}` · `cells:[{date,score}]`
  - `GET /energy` → `balance`
  - `GET /redeem/summary` · `GET /lottery/chances` · `GET /buddy/quota`
- 写：
  - `POST /tasks/accept` body `{"task_codes":[code,...]}`（**复数数组**，每次 ≤20 个）→ `results:[{task_code,status,message}]`
    - 旧的单数 `{"task_code": x}` 在新服务端一律 **400**；旧版把 `/tasks/accept` 当领奖用同样 400。
    - ⚠️ `results[].status` 的取值集**未枚举**：当前按「未知非空 status 归 failed」保守处理，真机抓到后收敛。
  - `POST /tasks/{task_code}/claim` body `{}` → `credit` · `energy` · `already_claimed`
    - 奖励**实发字段优先取响应**；`GET /tasks` 里的 `reward_credit` 只是活动配置，改版时会与实发不符。
  - `POST /buddy/travel/claim` body `{"record_id": <id>}` → `reward_credit`
  - **以下消耗不可逆资源或开启新流程，本仓暂未实现**：`POST /buddy/travel/depart`（开新旅程）· `POST /makeup-cards/use`（耗补登卡）· `POST /redeem`（连登兑换）· `POST /lottery/draw`（需防重放 `client_token`）· `POST /buddy/open`（耗能量）
- `accept_status` 枚举：`not_accepted | accepted | in_progress | completed | claimed`（**只有 `completed` 可领奖**）。
- 防重放：活动写接口需 `client_token`（形如 `u-<uuid4>`）；缺失时 `/lottery/draw` 直接 **400**。
- 核实：**2026-10-06**（字段与枚举）；**本仓尚未真机验证** ⇒ 待核。
- 代码：`internal/providers/workbuddy/growth.go`。

### 2.5 凭据格式

- 明文三形态：嵌套 `{account,auth}` · 扁平 snake_case · 扁平 camelCase（`internal/providers/workbuddy/credential.go`）。
- 新版桌面端会把 `accessToken` 写成加密信封 `{$wbEncrypted:1, envelope:"<base64>"}`（`suite=1`，即 `sym-v1`）。
  - **信封的密钥根只存在于桌面客户端的原生存储中**，无头构建不可获得 ⇒ 本项目**只做识别 + 明确报错**，不做解密（本项目只考虑服务器部署）。
  - **两代 scheme（2026-10-09 本机客户端 asar 实读）**：`sym-v1`（默认）与 `asym-v1`（公钥加密，携带 `fileKeyId` / `developerPublicKeyId`，仅 file / field framing）⇒ 识别层需覆盖两种形态。
- 核实：**2026-10-06**（形态与「密钥根不可得」结论）；**2026-10-09** 补录 `asym-v1` scheme（本机客户端 asar 实读）。

### 2.6 出站受查项与业务错误码（WorkBuddy）

**出站逐字指纹**（上游按**精确子串**拦截、非语义审核；一字改动即可绕过。净化实现：`internal/providers/workbuddy/sanitize.go`，默认开）：

| 指纹 | 形态 | 出站处理 |
|---|---|---|
| 客户端身份句（`You are Claude Code…` 句首、Codex CLI 指引句） | 完整句子 | 一词最小改写（语义不变） |
| SDK 计费头（`x-anthropic-billing-header` 键值 / 裸键名） | 键值 / 引用文本 | 键值整段剥离；裸键名缩写破形 |
| 尾随遥测键值（`cc_*=…;` 形态） | 键值串 | 整段剥离 |
| 反探测数字串 `11128` | 任意出现（即上游自身错误码） | 破形（加连字符）；**该串出现在请求体里本身就是拦截条件**，对话中合法提及也会被改写（无法两全） |

- 核实：**2026-10-06**（双仓同构情报对照 + 本仓字节级核验；作用面已覆盖 content / reasoning / 工具调用参数）。

**业务错误码台账**（本仓分类依据；`(status, code)` 组合回归见 `internal/providers/workbuddy` 的分类矩阵测试）：

| 码 | 含义 | 本仓分类 |
|---|---|---|
| `12153` | 会话失效（`Offline user session not found`；刷新 401 同族） | 认证；**单次不落死**（先核对凭据竞态 + 重试一次） |
| `11102` | 模型未注册 | 模型不可用（**不冷却账号**） |
| `11128` | 首条非 system / 反探测数字 | 请求级（触发**误报降级门**） |
| `11148` | 工具调用序列不匹配 | 请求级（序列修复为主） |
| `14018` | 额度已用尽（硬配额） | 配额（冷却至**次日 04:00**） |
| `6004` | 使用量超频率限制（响应含重置时刻文案） | 限流（按响应重置时刻） |
| `12001` / `12002` | 内容敏感（含敏感文案） | 请求级（触发误报降级门） |
| `10001` | 已签到 | 签到「已领」（非错误） |

- 核实：**2026-10-06 / 07**（上游实测痕迹 + 本仓分类回归矩阵锁定；精确业务码**优先于** HTTP 状态与文案判据）。

### 2.7 前缀缓存（WorkBuddy `prompt_cache_key`）

- 字段：chat 请求体 `prompt_cache_key`（字符串）。上游按该键缓存前缀，命中经响应 usage 报告（`cache_read_tokens`）。
- **实测（2026-10-09，CN 域 live 对照 ×3 轮 × 2 模型；出站录制证明键在请求体）**：
  - **无键时自动前缀缓存已经生效**（`deepseek-v4.1-flash` 稳定命中 >98%）——参照情报（「不带 → 命中 0、约 17× 费用差」）**未获复现**；
  - `glm-5.3` 命中**不稳定**（无键复问三轮：命中 / 0 / 0；带键三轮：0 / 命中 / 命中；带键缓存跨轮存活）；
  - **模型覆盖补记**：另覆核 `kimi-k3`（无键 98.7% / 带键 98.2%）与 `minimax-m3`（99.3% / 99.99%）——同样**无差异**；合计 4 个模型均未观察到注入键的稳定增量；
  - 结论：**注入无稳定收益** ⇒ 默认不启用。
- 本仓实现：`workbuddy/cachekey.go`（`AGENT2API_WORKBUDDY_CACHE_KEY=1` 才启用；键 `wb2a-<uid8>-<sha256(uid|会话) 前 16 字节 hex>`；客户端已带不覆盖）。复测工具：`cachekey_live_test.go`（`-tags live` + 导出凭据）。
- 核实：**2026-10-09**（真机 live 对照 + 单测 / 反向注入；默认关，运行时行为与旧版一致）。
